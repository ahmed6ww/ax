ax · agent package manager

Hardening the installer

A package manager writes executable configuration into the user's home directory from a remote source it never verifies. That is the whole audit in one sentence — everything below is detail and sequencing.

2,357 lines of Rust
19 source files
3 unit tests
0 integration tests
0 clippy warnings*
v1.5.0 · edition 2021

Verdict

The code is clean. The architecture is not.

Clippy passes with a single dead-code warning, so this is not a code-quality problem — it reads “old” because the design stopped at the demo stage and never grew the parts a package manager needs: an integrity model, an install ledger, a versioned registry protocol, and a transaction boundary.

Since this audit was first written, two findings have superseded everything else. ax writes Claude Code skills into the Claude Desktop directory on macOS and Windows, and writes Codex skills into ~/.codex/skills, which Codex does not scan. On the two targets the product is now betting on, installs report success and land where nothing reads them. See PATH-01 and PATH-02 — they gate every other item here.

The single dead-code warning is itself a shipped bug: ClaudeInstaller.global is never read, which means --global silently does nothing on the default target. That pattern — a flag or a feature that returns Ok(()) without doing the work — repeats across the codebase and is the source of most of the “not properly implemented” feel.

Register 01 — Security

Remote input reaches the filesystem and the shell

Everything agentpm install writes originates from an unauthenticated HTTP fetch, and nothing between the wire and fs::write validates it.

SEC‑01
Critical

Registry content becomes a command the editor will execute

The command, args and env of every MCP entry are copied verbatim from registry YAML into the user's Claude, Cursor and Codex configuration. The next time that editor starts, it launches the command. There is no allowlist, no signature, no digest, and no prompt showing the user what they are about to authorize — install.rs prompts for an API key but never for consent to run a binary.

A compromised registry repo, a hijacked account, or any MITM on the fetch is arbitrary code execution on every machine that installs the affected agent. The blast radius includes the scripts/ payloads downloaded into skill folders, which SKILL.md then instructs the agent to execute by path.

Fix Digest-verified manifests (see the registry format below), plus a trust gate that prints each command and requires confirmation unless --yes or a configured allowlist covers it. Add --no-mcp.

src/core/registry.rs:61 → src/installers/claude.rs:373-379 · cursor.rs:430-435 · codex.rs:251-257
SEC‑02
Critical

Path traversal from remote-controlled names

agent.name and skill.name arrive from registry YAML and SKILL.md frontmatter, then go straight into Path::join with no normalization. A skill named ../../.bashrc — or on Windows, an absolute path or a reserved device name — escapes the intended directory and overwrites arbitrary files with attacker-chosen content. The name is also interpolated into the remote fetch URL, so it can redirect the download itself.

Fix A single SafeName newtype validated at the parse boundary: ^[a-z0-9][a-z0-9._-]{0,63}$, rejecting ., .. and Windows reserved names. Parse it once in core so no installer can receive an unvalidated name.

src/installers/claude.rs:309,329 · codex.rs:194 · cursor.rs:371,394 · registry.rs:101,123
SEC‑03
Critical

No integrity verification anywhere in the chain

There is no checksum, no signature, no lockfile and no pinning at any hop: not on the registry index, not on agent manifests, not on downloaded skill files, and not on the release binary that install.sh pipes into /usr/local/bin. The GitHub release workflow publishes no SHA256SUMS and no build attestation, so even a diligent user has nothing to verify against.

Fix sha256 on every artifact, recorded in the registry index and re-checked after download; SHA256SUMS plus GitHub artifact attestation on releases; install.sh verifies before it moves the binary into place.

src/core/registry.rs:36-95 · install.sh:57-71 · .github/workflows/release.yml:89-100
SEC‑04
High

TOML injection in the Codex config writer

The Codex installer builds its config by string concatenation — format!("command = \"{}\"", tool.command) — over remote-controlled values. A quote or newline in a command, arg or env value closes the string early and injects arbitrary TOML into ~/.codex/config.toml, including additional [mcp_servers.*] sections the user never installed. The same function also appends blindly, so it grows without bound and can never update an existing entry.

Fix Serialize with the toml crate — already a dependency. Parse the existing document, merge, re-serialize.

src/installers/codex.rs:241-278
SEC‑05
High

A malformed user config is silently destroyed

Both JSON writers read the existing editor config and fall back to an empty object when parsing fails: serde_json::from_str(&content).unwrap_or_else(|_| json!({})). A trailing comma anywhere in the user's claude_desktop_config.json — or a file that is merely newer than what this parser understands — means agentpm install deletes every MCP server they had configured, with no error and no backup.

Fix Fail loudly on unparseable config and refuse to write. Never treat a parse error as an empty document.

src/installers/claude.rs:358-363 · cursor.rs:416-421
SEC‑06
High

Registry URL scheme is unrestricted

registry_url is read from ~/.agentpm/config.toml and used to build every fetch URL with no scheme check. A http:// or file:// value — set by a stray tutorial, a shared dotfile, or anything that can write that file — downgrades the entire trust chain to plaintext. The client is also built with Client::new(): no timeout, no retry policy, no redirect limit, no user-agent.

Fix Require https:// unless --allow-insecure-registry is passed explicitly. Build one shared client with a 30s timeout, capped redirects and a versioned user-agent.

src/core/config.rs:187-197 · registry.rs:19-33
SEC‑07
High

API keys are echoed, sprayed and stored world-readable

Three separate problems in one flow. The key is read with a plain read_line, so it echoes to the terminal and lands in scrollback and screen recordings. It is then written into every env value matching ${...}, so one key is copied into unrelated variables. Finally it is persisted in plaintext to the editor config with default permissions — mode 0644 on Unix.

Fix Masked prompt; substitute only the placeholder whose name matches; 0600 on any file containing a secret; and prefer leaving ${VAR} unexpanded so the key stays in the environment rather than on disk.

src/cli/commands/install.rs:90-106 · claude.rs:394 · codex.rs:278
SEC‑08
Medium

Config writes are neither atomic nor backed up

Every installer calls fs::write directly onto a live editor config. An interrupt or a crash mid-write leaves a truncated JSON or TOML file that the editor cannot load. Two concurrent agentpm install runs interleave and lose one another's writes.

Fix Write to a sibling temp file, fsync, then rename over the target. Keep a .bak of the previous version and take an advisory lock for the duration of an install.

Register 02 — Correctness

Features that report success without doing the work

These are the “not properly implemented” items. The common shape is a code path that returns Ok(()), prints a green check, and leaves the user with something incomplete.

PATH‑01
Critical

Claude Code skills are written to the Claude Desktop directory

Claude Code reads skills from ~/.claude/skills/<name>/SKILL.md on every platform, and project skills from .claude/skills/. claude_config_dir() instead returns ~/Library/Application Support/Claude on macOS and %APPDATA%\Claude on Windows — those are Claude Desktop paths. Linux is correct only by accident, via the ~/.claude fallback that runs when ~/.config/claude does not exist.

On macOS and Windows every install reports success and writes files Claude Code will never read. The same wrong root is used for agents/ and for the MCP config.

Fix ~/.claude on all platforms, honouring CLAUDE_CONFIG_DIR. Add project scope at .claude/. Never write to ~/.claude/skills/synced/ — that name is reserved for claude.ai sync.

src/utils/paths.rs:316-343 · claude.rs:96,322-324 · verified against code.claude.com/docs/en/skills
PATH‑02
Critical

Codex skills are written to a directory Codex never scans

Codex discovers skills in .agents/skills, walking from the working directory up to the repo root, then $HOME/.agents/skills, then /etc/codex/skills. ~/.codex/skills is not a skill location at all — ~/.codex holds config.toml and nothing else that matters here. Every Codex skill install has therefore been inert, on every platform, and macOS and Windows additionally resolve ~/.codex itself to a Desktop-style path that does not exist.

Fix Write skills to ~/.agents/skills/ and .agents/skills/; keep ~/.codex/config.toml for MCP only, and resolve it as a literal home-relative path rather than through dirs::config_dir().

BUG‑01
High

agentpm list panics on any non-ASCII description

The truncation slices by byte offset — &agent.description[..35] — which panics when byte 35 falls inside a multi-byte character. Every built-in agent description is ASCII, so this is invisible today; the first registry entry with an accent, an em-dash or an emoji crashes the command outright.

Fix Truncate on char_indices, or use a width-aware helper. Terminal width should also come from console rather than the hardcoded 85-column rule.

BUG‑02
High

--global does nothing on two of three targets

Only Cursor reads the flag. ClaudeInstaller.global is never read — the compiler says so — and CodexInstaller.global is silenced with #[allow(dead_code)]. Both always write to the user's home directory, so agentpm install foo and agentpm install foo --global produce identical results, and there is no project-scoped install for Claude at all.

BUG‑03

BUG‑05

Target architecture

Ports and adapters, with a transaction in the middle

The current layering is close — cli, core, installers, utils — but core reaches for the network and installers reach for it too, so there is no seam to test against and no place to put integrity checks. Moving I/O behind ports fixes both.

cli/ clap surface, TTY detection, exit-code mapping, and two output renderers — human and --json. No business logic.
↓
app/ Command orchestration: install, uninstall, update, list, sync. Owns the InstallSession — plan, stage, verify, commit, roll back.
↓
domain/ Pure types, no I/O: SafeName, Version, Digest, Manifest, Capabilities, TrustPolicy, Ledger, and the resolver. This is where every validation boundary lives, and it is unit-testable without a network.

adapters/ HttpRegistry wrapped in CachedRegistry, plus LocalRegistry for testing and private use · ClaudeRenderer / CursorRenderer / CodexRenderer over a shared skill module · AtomicFs · TtyPrompt.

The registry index that unblocks everything

One format change closes SEC-01, SEC-03, BUG-03, ARC-02, ARC-03 and ARC-09 simultaneously, because it turns resolution from guesswork into a lookup with an explicit, verifiable file list.

// ax-agents/index.json — fetched once, ETag-revalidated, cached
{
  "schema": 1,
  "updated": "2026-08-26T09:14:00Z",
  "agents": [{
    "name": "rust-architect",
    "latest": "1.2.0",
    "description": "Senior Rust systems engineer…",
    "versions": [{
      "version": "1.2.0",
      "manifest": "agents/rust-architect/1.2.0/agent.yaml",
      "digest": "sha256:9f2c1a…",        ← verified after fetch
      "files": [                          ← replaces the guess-list
        { "path": "skills/tokio-patterns/SKILL.md",
          "digest": "sha256:41ab7e…", "size": 2913 },
        { "path": "skills/tokio-patterns/scripts/lint.py",
          "digest": "sha256:c07e91…", "size": 1180, "exec": true }
      ],
      "mcp": [                             ← shown at the trust gate
        { "name": "context7", "command": "npx",
          "args": ["-y", "@upstash/context7-mcp"] }
      ]
    }]
  }]
}

The install pipeline

resolve   name@range → index lookup → concrete version
          fails closed: unknown name is an error, never a demo fallback

fetch     manifest + files, concurrently, through the cache
          every response checked against its declared digest

gate      print each MCP command and each executable file
          confirm unless --yes or the command is allowlisted

stage     render per target into $TMP/ax-<uuid>/
          SafeName has already made traversal unrepresentable

commit    fsync → rename → append to ~/.agentpm/state.json
          any failure replays the journal backwards
Why the trust gate matters more than the digest. Digests prove the file is what the registry published; they say nothing about whether the registry should be trusted. Since installing an agent authorizes a command to run on the user's machine, that authorization has to be visible at least once. Showing the command and requiring a keypress is the difference between a package manager and a remote-execution service.

Two decisions worth making before P2

  • Is the registry a git repo or a service? Raw-GitHub is free, cacheable and needs no operations, but it cannot do search, download counts, or namespaced publishing — and it is why resolution is guesswork today. A signed static index on a CDN keeps the zero-ops property while removing the guessing; a service is only worth it once agentpm publish exists. Recommendation: static signed index now, service at P4 if publishing takes off.
  • Does an agent get to ship executable scripts? Today it does, silently. The honest options are to keep it behind the trust gate with the executable files listed explicitly, or to drop scripts/ and make skills declarative-only. The first is more useful; the second is far easier to secure. Deciding this changes how much of the trust gate needs to exist.
